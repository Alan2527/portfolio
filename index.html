IA aplicada a QA

La IA como parte del flujo de trabajo, no como reemplazo

Integro asistentes de IA en el día a día del testing para cubrir más en menos tiempo. Estas son las tareas concretas en las que me apalanco y, sobre todo, el criterio con el que valido lo que producen.

Claude Gemini ChatGPT

🧪Diseño de casos y edge cases

Genero variantes de casos a partir de los requerimientos y del historial de defectos, para descubrir escenarios límite que se escapan de la lectura manual de la especificación. Después los reviso y descarto los que no aportan riesgo real.

🔧Mantenimiento y refactor de suites

Uso IA para refactorizar código de tests, extraer helpers repetidos y actualizar selectores cuando cambia el front, lo que baja mucho el costo de mantener una suite viva a lo largo del tiempo.

🔎Análisis de fallas y logs

Ante una falla, apoyo el diagnóstico pasando el stack trace, los logs y la evidencia para acotar hipótesis rápido y distinguir un bug real de un problema del propio test.

📝Redacción de reportes de defectos

Acelero la escritura de reportes claros y reproducibles: pasos, resultado esperado contra obtenido y clasificación de severidad, en un lenguaje que el equipo de desarrollo pueda accionar sin ida y vuelta.

📊Cobertura y priorización

Contrasto la cobertura existente contra los flujos críticos del negocio para detectar zonas sin pruebas y decidir qué conviene automatizar primero.

⚙️Scripting y tooling propio

Construyo utilidades de apoyo — parsers de resultados, comparadores, generadores de datos de prueba — que sin IA no serían rentables en tiempo para un proyecto puntual.

El criterio sigue siendo humano

La IA acelera, no decide. Todo caso generado se revisa antes de ejecutarse y ninguna suite se da por buena porque "los tests pasan": un test puede pasar validando lo incorrecto. Antes de automatizar defino qué es importante para el usuario, y valido que la evidencia respalde de verdad lo que el reporte afirma. Ese control es justamente lo que distingue a un QA de una herramienta.

Motor de Regresión Visual

Herramienta propia (Selenium + Pillow) que detecta regresiones visuales entre dos versiones del mismo sitio. En vez de comparar píxel contra píxel — que genera falsos positivos con cualquier diferencia de renderizado — recorre el DOM y compara elemento por elemento su geometría y sus estilos computados, clasificando cada diferencia por tipo. El informe es interactivo: al hacer clic en una diferencia se resalta el elemento exacto sobre la captura.

Detección de defectos

Un defecto detectado por cada proyecto

Tres tipos de defecto muy distintos — de interfaz, de contrato de API y de layout — cada uno detectado por una de las suites de arriba y documentado como lo reportaría en un equipo. Todos son verificables: se indica el test que lo expone y podés abrir el reporte en vivo para ver la ejecución.

BUG-01 · E2E · Catálogo Severidad crítica

Todos los productos del catálogo muestran la misma imagen rota para un perfil de usuario específico

Pasos para reproducir
  1. Iniciar sesión con el usuario problem_user.
  2. Observar la grilla de productos del inventario.
  3. Comparar el atributo src de las 6 imágenes.
EsperadoCada producto muestra su propia imagen; las 6 URLs son distintas.
ObtenidoLas 6 imágenes apuntan a la misma URL, un recurso 404.
Evidencia
AssertionError: Las 6 imágenes apuntan a:
{'https://www.saucedemo.com/assets/sl-404-Cq1a9k9X.jpg'}
assert 1 == 6
Suite E2E · test_imagenes_unicas — marcado xfail estricto: si el defecto se corrige, el pipeline avisa.
BUG-02 · API · Contrato Severidad media

La autenticación devuelve 200 ante credenciales inválidas en lugar de un código de error

Pasos para reproducir
  1. Enviar POST /auth con un usuario válido y una contraseña incorrecta.
  2. Inspeccionar el código de estado y el cuerpo de la respuesta.
Esperado401 Unauthorized, siguiendo la convención REST para credenciales rechazadas.
Obtenido200 OK con un campo reason en el cuerpo y sin token.
Evidencia
POST /auth
Status: 200

--- Response ---
{
  "reason": "Bad credentials"
}
Suite de API · test_credenciales_invalidas — un cliente que valide solo por código de estado interpretaría el login como exitoso. Fijado con assert documentado.
BUG-03 · Regresión visual · Layout Severidad crítica

Las imágenes del catálogo cambian de ancho entre versiones y rompen la grilla de productos

Pasos para reproducir
  1. Capturar la versión base del inventario y la versión candidata.
  2. Ejecutar la comparación por elemento con tolerancia 0px.
  3. Revisar las diferencias clasificadas como tamaño.
EsperadoLos img.inventory_item_img conservan su ancho de 159px entre versiones.
ObtenidoLos 6 elementos pasan a 262px de ancho, desplazando el resto de la tarjeta.
Evidencia
img.inventory_item_img — TAMAÑO · ANCHO
159px  →  262px   (×6 elementos)
Motor de regresión visual · detectado por comparación de geometría, no de píxeles: no lo dispara ninguna diferencia de renderizado.
